Part 3The coverage criteria — from weakest to strongest

    
Each criterion subsumes the ones below it. The triangle code is a great illustration of why statement/branch is not enough.

    

      

        
Path — every route (loops → infeasible)

        
Multiple-condition — all 2ⁿ rows of a decision

        
MC/DC — each condition flips the outcome (~n+1)

        
Condition/Decision

        
Branch / Decision — every T & F edge

        
Statement — every node

        
stronger ↑ · subsumes everything below

      

      

        
On the triangle code

        

          
CriterionWhat it asks here

          
            
Statementreach all 5 returns + 4 decisions (5 tests do it).

            
Branchtake T and F of each if (still 5 tests).

            
Conditionmake each atomic term — a+b≤c, a==c… — both true and false.

            
MC/DCa test where only a==c is true, so it alone flips “Isosceles”.

            
Boundarya test at a+b == c (e.g. 1,2,3) — the case ≤ vs < depends on.

          
        

        
The weak 5-test suite reaches 100% statement & branch — yet misses condition, MC/DC and boundary cases. Part 4 shows what slips through.

      

    

  


  
  

    
Part 4Mutation testing — inject a bug, see if a test notices

    
A mutant is the same code with one tiny edit. Run your current suite against it: if some test now fails, the mutant is killed; if the whole suite still passes, it survived — a real gap. Load a suite, then inject.

Load a suite and press Run all mutants. Try the WEAK suite first (100% coverage) — two mutants survive. Then load STRONG.

        
Why survivors slip past 100% coverage

        
A surviving mutant still executes the changed line — coverage is happy. It survives because no test asserts a value that the change would alter (a missing boundary or condition case). Mutation is behavioural; coverage is only structural.
